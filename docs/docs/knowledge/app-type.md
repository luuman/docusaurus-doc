# 安装包

## windows

- **EXE (NSIS)**：**灵活的传统安装包**。适合广大普通软件开发者，追求高度自定义的安装界面和流程。
- **MSI**：**企业部署的标准**。适合需要大规模、静默、统一部署和管理软件的企业环境。
- **APPX**：**现代应用商店的沙盒包**。适合通过 Microsoft Store 分发，强调安全、隔离和自动更新的现代应用。

---

### 详细对比

| 特性维度         | EXE (以 NSIS 为例)                                                                                               | MSI                                                                                                                                     | APPX (及其后继者 MSIX)                                                                                                                                       |
| :--------------- | :--------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心定位**     | 灵活、通用的脚本化安装程序                                                                                       | 企业级、标准化的软件部署                                                                                                                | 安全、沙盒化的现代应用分发                                                                                                                                   |
| **分发渠道**     | 开发者官网、第三方下载站等                                                                                       | 企业内网（SCCM, Group Policy）、下载站                                                                                                  | **Microsoft Store** (主要渠道)                                                                                                                               |
| **安装体验**     | **高度可定制**。安装向导（欢迎页、许可协议、安装路径、组件选择）、卸载程序完全由脚本定义。                       | **标准化**。通常使用 Windows 内置的通用安装向导，界面统一且简陋。                                                                       | **简单化**。用户点击“获取”后几乎无需交互，自动安装。被称为“零点击安装”。                                                                                     |
| **技术本质**     | 一个可执行文件，内部包含压缩的软件文件和一套**脚本指令**。安装时解压文件并执行脚本（如写注册表、创建快捷方式）。 | 一个**关系型数据库**，包含文件、注册表项、自定义动作等**标准化数据表**。安装过程是系统服务 `Windows Installer` 根据数据库内容执行操作。 | 一种**容器化**的包格式。基于 `.zip` 压缩，包含应用文件、清单文件（声明依赖、权限等）。安装后运行在**沙盒**环境中。                                           |
| **静默安装**     | 支持，但参数**因包而异**（常见如 `/S`）。依赖制作人是否实现。                                                    | **原生支持且标准化**。参数统一为 `msiexec /i package.msi /qn`。这是其**核心优势**。                                                     | 主要通过商店或 PowerShell 命令（`Add-AppxPackage`）部署，对企业部署友好。                                                                                    |
| **权限要求**     | 通常需要**管理员权限**，因为它可能向系统目录和注册表写入数据。                                                   | **必须**需要管理员权限，因为它会修改系统级的设置和文件。                                                                                | **不需要**管理员权限。所有文件都安装在用户隔离的空间内，通过声明的能力（Capabilities）有限制地访问系统资源。                                                 |
| **文件与注册表** | **任意读写**。可以安装到任何位置（如 `Program Files`），并向注册表任意位置写入信息。                             | **任意读写**。同样可以安装到系统位置并修改注册表，但所有操作都被记录在 MSI 数据库中，便于卸载清理。                                     | **高度隔离**。应用安装在自己的“容器”内（`C:\Program Files\WindowsApps`），无法修改系统注册表或影响其他 APPX 应用。使用虚拟化 registry 和文件系统。           |
| **依赖管理**     | 通常将依赖（如 VC++ Redist, .NET Framework）**打包**在安装程序内，并自行安装。可能导致版本冲突。                 | 依赖可以作为“合并模块”打包，或通过启动条件检查，但管理起来相对复杂。                                                                    | **依赖声明**。在清单中声明所需的系统框架依赖（如 .NET UWP），商店或系统会**自动处理**依赖安装。                                                              |
| **更新机制**     | 由开发者自行实现。常见方式有：1. 内置更新功能。2. 提示用户下载新版本安装包覆盖安装。                             | 通过企业部署工具（如 SCCM）**推送更新包**（MSP）。                                                                                      | **由 Microsoft Store 自动管理**。后台自动下载和安装更新，用户无感。                                                                                          |
| **卸载清理**     | 依赖于安装脚本的编写质量。通常可以清理干净，但劣质脚本可能残留文件和注册表项。                                   | **非常干净**。因为 `Windows Installer` 服务严格记录了所有安装项目，可以精准删除。                                                       | **绝对干净**。卸载会删除整个容器，100%无残留。                                                                                                               |
| **安全性**       | 较低。安装包可能被植入恶意软件，安装过程可能对系统进行任意修改。                                                 | 中等。MSI 本身是标准格式，但内容仍需审计。安装过程仍需高权限。                                                                          | **非常高**。包由商店签名认证，运行在沙盒中，权限受限，极大减少恶意软件的风险。                                                                               |
| **适用场景**     | - 共享软件、免费工具、游戏- 需要复杂安装界面（如选择组件）的软件- 独立开发者和小团队                             | - **企业、政府、教育机构**的大规模软件部署- 需要严格管理和审计软件资产的环境                                                            | - 提交到 **Microsoft Store** 的 UWP 或 PWA 应用- 需要**安全、简单、自动更新**体验的现代应用- **Win32**、**WPF** 等传统应用也可通过 **MSIX** 打包获得类似优势 |

### 补充说明：MSIX - 未来的方向

值得注意的是，微软正在大力推广 **MSIX**，它是 APPX 的进化版，**融合了 MSI 和 APPX 的优点**：

- **像 MSI 一样**：可以打包传统的 Win32、WPF、WinForms 桌面应用，并支持复杂的安装脚本。
- **像 APPX 一样**：提供容器化、安全、可靠的安装和更新体验，以及干净的卸载。

MSIX 旨在成为未来 Windows 应用打包的**统一标准**，逐渐弥合传统桌面应用和现代商店应用之间的鸿沟。

### 总结与选择建议

- **如果你是一个普通用户**：

  - 从网上下载软件，遇到的大多数是 **EXE** 安装包。
  - 在公司电脑上，IT 部门为你静默安装的软件很可能是 **MSI**。
  - 从 Microsoft Store 下载的应用都是 **APPX/MSIX**。

- **如果你是一个开发者/软件发布者**：
  - **EXE (NSIS, Inno Setup 等)**：如果你的软件主要面向个人用户，需要通过自己的网站分发，并且需要高度定制的安装流程（比如安装游戏 MOD、选择组件），这是最经典和灵活的选择。
  - **MSI**：如果你的软件客户主要是企业，需要集成到他们的 Active Directory 或 SCCM 中进行批量部署和管理，**MSI 是唯一的选择**。
  - **APPX/MSIX**：如果你希望通过 Microsoft Store 分发，或者希望为用户提供最安全、最现代（自动更新、无残留）的安装体验，尤其是开发 UWP 应用，那么必须使用 APPX/MSIX。对于传统桌面应用，也强烈推荐尝试用 **MSIX** 打包。

好的，安装路径是这三者一个非常核心且直观的区别。我们来详细分解一下：

### 核心结论

| 安装包类型     | 典型默认安装路径                                                 | 路径灵活性   | 本质原因                                                       |
| :------------- | :--------------------------------------------------------------- | :----------- | :------------------------------------------------------------- |
| **EXE (NSIS)** | `C:\Program Files\<软件名>` 或 `C:\Program Files (x86)\<软件名>` | **非常高**   | 由安装脚本作者完全控制，可以安装到任何位置。                   |
| **MSI**        | `C:\Program Files[\ (x86)]\<软件名>`                             | **低**       | 遵循 Windows 规范，路径通常由系统决定，用户难以更改。          |
| **APPX/MSIX**  | `C:\Program Files\WindowsApps\<包全名>`                          | **几乎为零** | 强制沙盒化安装，路径由系统严格管理，用户完全不可见且不可更改。 |

---

### 详细解释

#### 1. EXE (NSIS) - 高度自由，脚本决定

- **默认路径**：通常安装程序会提供一个默认路径，如 `C:\Program Files\MySoftware`。但这个路径**完全由脚本编写者决定**，他可以设置为任何路径。
- **用户选择**：在安装向导中，几乎总会有一个步骤让用户**自定义安装目录**。用户可以选择 `D:\MyPrograms`、`C:\MyApp` 或任何他有写入权限的位置。
- **技术原因**：NSIS 安装程序本质上是一个解压程序加脚本执行器。脚本里写了一行 `InstallDir "$PROGRAMFILES64\MySoftware"` 来设置默认路径，又提供了一个页面 (`Page directory`) 让用户修改这个路径。最后，它就把文件解压到用户选择的那个路径里。
- **特点**：**灵活但不规范**。不同软件可能安装到不同地方，全靠开发者自觉遵循规范。

#### 2. MSI - 企业规范，路径固化

- **默认路径**：严格遵循 Windows 标准。64 位系统上的 64 位程序会安装到 `C:\Program Files\`，32 位程序会安装到 `C:\Program Files (x86)\`。具体的安装文件夹名称在制作 MSI 包时就已确定。
- **用户选择**：**用户通常无法更改具体路径**。在安装时，你可能只能看到一个将要安装到的“目录”，但**没有浏览按钮让你修改它**。高级用户可以通过命令行参数 `TARGETDIR` 来指定，但普通用户不会这么做。
- **技术原因**：这是由 MSI 的“企业部署”基因决定的。为了便于大规模统一管理，IT 管理员希望所有电脑上的某个软件都安装在**完全相同的路径**下，这样配置脚本、路径依赖都不会出错。如果每个用户都能随便改路径，管理会变得一团糟。安装路径等信息是存储在 MSI 数据库表中的硬编码值。
- **特点**：**标准化且固定**。牺牲了灵活性，换来了统一性和可预测性，这是企业环境的核心需求。

#### 3. APPX/MSIX - 沙盒隔离，系统托管

- **默认路径**：**所有 APPX/MSIX 应用都必须安装到系统管理的隐藏文件夹中**：
  `C:\Program Files\WindowsApps\<PackageFullName>`
  其中 `<PackageFullName>` 是一个很长的、带版本号和发布者标识的名字，例如 `Microsoft.WindowsCalculator_10.2103.8.0_x64__8wekyb3d8bbwe`。
- **用户选择**：**用户绝对无法更改安装路径**。你甚至都看不到这个路径（`WindowsApps` 文件夹默认对用户是隐藏且无权限访问的）。在安装过程中，**根本没有选择路径这一步**。
- **技术原因**：这是实现**安全沙盒化和可靠更新/卸载**的基础。
  1.  **安全**：将所有文件封存在一个独立的、权限严格的容器中，防止应用篡改系统或其他应用的文件。
  2.  **可靠性**：系统完全掌控这个文件夹，可以确保在更新或卸载时，**100%干净地处理所有文件**，不会有任何残留。
  3.  **依赖管理**：应用所需的框架等依赖也一起安装在容器内，避免与系统全局环境的版本冲突。
- **扩展存储**：虽然应用**本体**必须安装在系统盘，但对于游戏等大型应用，其**下载内容 (DLC)** 或大型数据文件可以设置存储在其他驱动器。这是在安装后，在应用的“设置”里进行管理的，而不是在安装过程中选择路径。
- **特点**：**绝对隔离和系统托管**。路径对用户透明，彻底杜绝了因为安装路径问题导致的软件故障，是现代化应用管理的体现。

### 总结对比

| 行为                   | EXE (NSIS)                       | MSI                                  | APPX/MSIX                            |
| :--------------------- | :------------------------------- | :----------------------------------- | :----------------------------------- |
| **能自己选装在哪吗？** | **可以**，安装时有选择界面       | **基本不行**，只能装在程序固定目录   | **绝对不行**，完全由系统决定         |
| **能装到 D 盘吗？**    | **可以**，用户自己选就行         | **很难**，需要管理员通过高级方式部署 | **本体不能**，但部分数据可以         |
| **路径规范吗？**       | 看开发者心情，可能很乱           | **非常规范**，统一在`Program Files`  | **极度规范**，统一在`WindowsApps`    |
| **为什么这么设计？**   | 为了给**用户**和开发者最大灵活性 | 为了给**企业 IT 管理员**提供统一性   | 为了给**操作系统**提供安全性和可靠性 |

因此，从安装路径这一点，你就能清晰地感受到三种格式背后不同的设计哲学：**用户自由**、**企业管控**和**系统安全**。
